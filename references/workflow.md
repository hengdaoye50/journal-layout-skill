# 完整流程与工程纪律

这份文档记录的是**怎么把一套排版工作组织成可重复的工程**，而不是某一次排版的流水账。
SKILL.md 给了七步框架；这里给每一步的判断标准、目录约定和交付清单。

## 0 项目目录约定

```
<论文名>/
├── 01_四刊最终稿/          交付物，每刊一个 docx，文件名带刊名
├── 02_投稿指南与例文/       每个刊一个子目录：投稿须知 docx + 已刊例文 pdf
├── 03_历史稿与原稿/         每批次改动前的整份留档，目录名 = 日期_阶段前
├── 04_论文图件/            每版图一个子目录：SVG 源 + PNG 成品 + 设计说明.md
├── 05_版式检查与预览/       校验报告、抽页预览、对照页
└── 06_处理脚本与临时数据/    一次性脚本、中间 docx、测量用的 xml
```

为什么这样分：`03` 让每次改动都能回退；`04` 让图的每次迭代都有设计理由可追；
`06` 让"跑过的脚本"和"交付物"分开放，避免半年后不知道哪个 docx 是最终稿。

留档目录命名带日期和阶段，例如 `2026-11-07_机制图重构前`——顺序读下去就是这部稿子的改造史。

## 1 素材阶段：先要例文，再谈版式

排版需求的本质是"模仿一个具体出版物"。所以第一步不是改 docx，是把依据找齐：

- 官方投稿须知（docx/pdf）：给规则，但常与真实刊出版式有出入（字号、行距尤其常见）
- 已刊例文（pdf）：给真相，优先级最高
- 已有成品（如果做过）：给"上次是怎么处理的"，是三者冲突时的仲裁参考

三者冲突时的处理顺序：**例文实测 > 投稿须知 > 惯例**。
冲突本身要写进 `references/journal-specs.md` 的对照表，而不是悄悄选一个。

## 2 底稿阶段：语义先行，数值后置

不要直接在成品 docx 上套第二个刊的版式。正确做法是维护一份"语义干净"的底稿：

- 题名、一级标题、二级标题用 Word 的 Title / Heading 1 / Heading 2 样式
- 正文是普通段落，不带任何字体字号硬设置
- 图表题注是独立段落，以"图1"/"表1"开头
- 参考文献是独立章节
- 页下注在底稿阶段就是真正的 footnote

有了底稿，四刊版本 = 同一份底稿 × 四组参数。改一个刊的版式不会污染另一个刊，
改正文也只改一处。

判定底稿是否合格：`md2docx.py` 跑完后，`journal_layout.py --dry-run` 的段落分类
应该只有 title/h1/h2/h3/body/abstract/keywords/caption/ref_head，没有大量误判。

## 3 套版阶段：参数与算法分离

先确定目标形态，再动手：

- **投稿版式**（`--mode submission`，`SPECS`）：交编辑部的稿子，字大、单栏、行距松
- **刊出版式**（`--mode published`，`PUBLISHED_SPECS`）：仿已刊 PDF 的真实样张，小字密排、可能双栏

两者字段结构完全一致，只是数值不同。判断依据：用户说"投稿/送审"选前者，
说"像刊出来的样子/仿样张"选后者；说不清就问。

`journal_layout.py` 里参数表是唯一该改的地方。加一个刊 = 加一个 dict，
不需要动任何函数。字段含义：

| 字段 | 含义 | 缺省行为 |
|---|---|---|
| `page` / `margins` | 页面尺寸与四边距（pt） | `None` → 保持原值并提示 |
| `body` | 正文 east 字体、字号、固定行距、首行缩进 | 同上 |
| `title` / `h1` / `h2` / `h3` | 各级标题的字体字号、对齐、缩进、段前段后 | 同上 |
| `abstract` | 摘要区字体、左右缩进、`rename` 标签替换 | 同上 |
| `caption` / `table_cell` | 图表题注与表格单元格 | 同上 |
| `footnote` | 页下注 `numFmt`（圈码）、`numRestart`（逐页重编）、字体字号行距 | 同上 |
| `figure` | 图题在图上方还是下方（只指图题，表题恒在上方）、图宽 | 同上 |
| `columns` | 1 单栏 / 2 双栏 | `None` → 不分栏 |
| `columns_start_at` / `span_tables` / `span_figures` | 双栏从哪个一级标题起、表和图是否通栏 | — |
| `column_space` | 栏距，**单位是 twips 不是 pt**（22.7 pt = 454 twips） | 360 |

**"缺省即跳过"是故意的。** 一个刊没确认的项，脚本不会替你编一个值，
verify 也不会拿它判你错，而是把该项列进"未核对项"。这样交付时你能准确说出
"哪些是核过的，哪些是没依据的"。

## 4 验收阶段：结构断言 + 局部看图

验收分两层，顺序不能颠倒：

**第一层：结构断言**（`verify_layout.py`，必做）
页面、边距、每类段落的有效字体字号行距缩进、分栏、页下注编号与样式、
图宽是否超通栏、图题与表题位置、三线表竖线、正文文本完整性。

关键设计：读的是**有效格式**——run 上直接设的 → 段落样式 → 样式继承链。
因为 Word 里大量格式落在样式上，只读 run 会把"正确继承"误判成"未设置"。

**第二层：抽页看图**（`render_preview.py`，按需）
只回答结构断言管不了的问题：图是不是挤到了页底、表格有没有被跨页切断、
双栏区段的首尾是否自然。默认出首页+末页，`--pages` 指定可疑页。

这一层要克制。曾经为了"保险"把三十页全渲染成 PNG 逐页看，结果是：慢、贵、
而且真正的问题（0.5pt 字号差、行距不是固定值）肉眼根本看不出来——那些问题恰好
全在第一层就能断言。**图的用法是"定位一下"，不是"过一遍"。**

## 5 交付清单

- [ ] 每刊一个 docx，文件名含刊名，放在 `01_四刊最终稿/`
- [ ] 每刊 `verify_layout.py --strict --ref 底稿.docx` 全绿
- [ ] `snapshot.py --diff` 证明只有声明过的部件变化
- [ ] 未确认项逐条向用户说明（不要把"没依据"包装成"已符合"）
- [ ] 图件的"图中关系 / 正文依据 / 表达边界"核对表已填
- [ ] 交付说明里写清：每刊版式差异、与上一版相比改了什么、怎么重跑

## 6 重跑约定

给用户一条能自己重跑的命令，而不是一堆散脚本：

```bash
python .work/driver.py            # 全量
python .work/driver.py 03         # 只重排第 3 篇
```

driver 的职责是把"每篇 → 底稿 → 套版 → 校验 → 出 PDF"串起来，
失败就停在那一步并打印原因。单个脚本不该感知"批量"。
